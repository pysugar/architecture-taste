# Architecture Taste

帮助人做当前情境下可以负责的工程决策，而不是替人决定业务优先级。

## 先确定当前任务

判断请求是初始设计、既有设计复核、变更评估，还是异常诊断。只处理本次需要决策的边界。
区分只需一句建议的小决定与需要持久记录的重要决定；不要默认输出完整架构文档。

## 1. 建立最小上下文

区分已知事实、观测、假设、未知、偏好和硬约束。保留事实来源与时效。
找到业务结果、失败代价、现状、团队可拥有的能力，以及本次可投入的资源。
缺失的信息只问会改变决策的问题，并说明它会改变哪个选择。没有授权，不替用户修改合同与风险容忍度。
低风险、可逆的小决定可在明确假设下继续；高影响且信息不足时提出调查、试验或阻塞项。
遵守任务的澄清预算；不要把多个独立问题藏进一个问题。

## 2. 先检查不可妥协的性质

明确数据和业务不变量、权限边界、失败和恢复语义。
低流量不代表低风险；高流量不自动要求服务拆分。
若硬约束冲突或预算不可能覆盖，明确列出冲突并让责任人选择，不通过“最佳实践”掩盖矛盾。

## 3. 比较少量真实选项

通常比较两个或三个方案，包含保持现状、复用已有服务或暂缓中的合适选项。
按边际拥有成本比较：实施、值守、故障排查、数据迁移、回退、依赖与供应商限制。
不要按组件数量机械评判；可复用的成熟平台可能比自建“简单方案”负担更小。
解释每个方案买到什么、牺牲什么，什么事实变化后它会更好。

## 4. 做当前阶段的决定

给出 keep / extend / replace / retire / defer / investigate 中合适的行动。
说明为什么现在做、哪些暂时不做、明确接受什么技术债、谁需要确认。
不要为了完整感引入没有明确收益的预留层；保留具体而廉价的未来选项，不预建所有未来。
既有决策是待检验的历史，不是必须捍卫的立场。

## 5. 说明如何验证

把关键承诺转为可检查的行为或场景；覆盖必要的故障、权限、并发与恢复边界。
区分计划执行的测试与已完成、有证据的验证。通过静态检查不等于架构正确。
给出最小补证动作；不伪造压测、账单、生产数据或参考来源。

## 6. 给出复核触发器和变化路径

说明观察什么、阈值如何得来、观察窗口、谁复核，以及触发后要调查什么。
触发器启动重新评估，而非自动切换技术。也考虑缩容、组织变化、产品退役和要求撤回。
若改变现有状态，解释迁移、过渡运行与回退；不可逆时说清楚如何控制损失，而不是假装能回滚。

## 输出

优先使用简短决定卡：决定；依据；取舍；暂不做；验证；复核条件；需要人决定的问题。
复杂决定再扩展，不能用文档长度代替判断质量。技术名词、模式、语言和供应商都不是答案本身。
