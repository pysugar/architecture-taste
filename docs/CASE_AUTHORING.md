# 案例写作与复核

## 最小案例单位

一个案例围绕一条真实可理解的业务线，至少明确当前决定、已知条件、约束和失败代价。一个阶段只考几个相关取舍，不同时塞入所有分布式系统名词。

JSON 是机器可验证的题库事实源。人可另写背景说明，但不要维护两份相互独立的同名事实。

`public` 是参评者初始知道的信息；`oracle` 是可通过澄清取得的事实；`reviewer` 是作者对关键约束、可接受方案族和错误边界的说明。三者不能混写。

所有当前案例都为 synthetic，给出的测量也是合成观测。不要把 `scenario_observation` 改成“生产实测”来增加可信度。

## 作者必须区分

事实：明示的团队规模、环境、约束；观测：给定的延迟、资源消耗等证据；假设：尚待验证的判断；未知：确实未给出；偏好：可协商的方向；硬约束：不能由 Agent 擅自牺牲的要求。

每条约束标明 owner 和 hard/soft。与法律或监管有关的真实要求必须查证并给来源，本基座不凭空创设任何法定义务。

观察到 CPU 高不自动证明瓶颈归因；观测与因果结论分开。给出 DAU 而不给请求形态、峰值和关键负载，通常无法支撑精细容量判断。

## 一个有效阶段应当具备

一个可以立即继续的合理选项；至少一个在本阶段不合适、但在另一个情境中可能合适的选项；少量真正改变决定的未知；能说明不变量的故障或业务场景；允许条件性决定而非强迫选边。

如果任何熟悉架构的模型都能从关键词直接猜答案，降低知识问答占比，增加有意义的上下文变化。如果两位评审者都只能依赖个人喜好分高低，补事实或承认方案并存。

## 演化的约束

阶段变化应当明确：哪些事实失效、哪些仍有效、哪些是新目标、哪些只是某位利益相关者提出的愿望。新时期不是把所有旧要求清零。

不要把单体→微服务→多活设成默认进度条。至少有一个阶段允许保持现状、收缩或退役。也至少有一个低流量但必须严谨保障语义的场景。

后续阶段不能假定参评者采用某个教师答案。当前工具不会执行架构，也不会计算其运行后果；遇到不适配的叙事，先标注一致性问题，不偷偷改写历史。

## 反事实变体

每个变体只改变一个可解释的决策轴，如是否有可复用的平台与值守能力。为了保持一致性，相关文字和 oracle 必须一起更新，但不要顺便改变工作负载、预算和 SLA 让因果无法解释。

变体不强迫选择翻转。观察的是理由是否响应新前提，原先条件消失以后是否还被引用。

## 审阅状态

初稿一律 `unreviewed`。设为 reviewed 前记录谁看了、看了什么、有什么分歧，以及是否复核了数据一致性和可接受解空间。AI 生成初稿并通过 JSON Schema，不构成人工领域审阅。

修改案例后增加 Git 提交并重新导出试验；SHA-256 不匹配不能继续衔接旧轨迹。关键要求修改应写明原因，不能为了让某组答案更好看而事后调整。

## 保留负面资产

记录“不该迁移但迁移了”“应该增强却只说简单就好”“问了十个不改变决定的问题”“忽略已有平台”“为了坚持旧选择而拒绝新事实”。这些失败模式比技术名词列表更有训练与复核价值。

记录来源与授权。先用原创合成例子；引入真实项目时，不把公司的内部代码、事故或客户信息自动变成公开案例。
