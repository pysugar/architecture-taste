# 实验协议 v0.1

## 1. 初始试验回答什么

同一个模型在相同事实与预算下，完整方法是否比普通提示和简版 ADR 更有用？先隔离这个问题，再研究自动上下文检索和模型差异。

| 组别 | 输入变化 | 解释边界 |
|---|---|---|
| `baseline` | 普通架构建议提示 | 是轻量对照，不是“故意让模型表现差”的无意义提示 |
| `adr` | 简版 Context / Decision / Status / Consequences | 判断改善是不是仅来自一般的结构化记录 |
| `taste` | 完整实验性 Skill | 评估额外流程的增量价值及其代价 |

公共任务边界、回答语言、已公开事实、阶段历史规则、工具和模型设置应一致。输出自然语言即可。不要只让 taste 组获得更长运行时间、额外工具或答案样例。

这能测“整个指令包的效果”，不能完全分离长度和语义。若观察到增益，下一轮再加入等长安慰剂/删减对照，区分哪些条款有用。

## 2. 两条试验轨道不能混报

### Full-context：判断能力

一次性给出**当前阶段**的 public 和全部可披露 oracle 答案；不给评分笔记、未来阶段和反事实评分说明。三个组拿到同一事实集合。

这里的“完整”仅指作者为本阶段设置的已知事实，不是全知。明确写为未知的信息仍然未知，不允许虚构。

### Clarify：获取信息 + 判断

初始只给 public。每个阶段最多三次原子问题，由人将自然语言问题映射到预写 oracle 答案。模型不知道答案菜单。

操作员不能临场补写对某组更有利的事实。同义问题映射同一条；复合问题拆成原子问题，逐条计费；重复问题和无法回答的问题都消耗预算。工具计数，但**复合问题拆分与语义映射由操作员负责**。

遇到题库未覆盖的新问题，回答 UNKNOWN 并记录。后续完善案例必须增加版本并重开所有受影响试验，不能用补充信息只续跑某一组。

两组因提问不同得到不同信息，是此轨道测量的一部分。评审时区分“信息没获取到”“事实已知却判断错了”；不可把隐藏事实当作所有参评者都知道。

## 3. 跨阶段回放

T0 后原样保存回答。T1 必须携带该组**实际产生的** T0 回答，T2 携带其实际 T0/T1，而不是作者期望答案。不同 arm、model、trial 和案例版本不能串接。

v0.1 只是叙事式阶段练习，**不是因果环境模拟器**。后续变化为作者设定的外生事件；工具并未部署上一步方案，也未由上一步操作计算新的运行状态。

若下一阶段的叙述与参评者先前方案不兼容，操作员应标为“场景一致性待复核”，参评者也可指出矛盾。不得把作者预设路线强塞成“你上次做了什么”，更不能借此扣分。需要真实动作改变后续世界状态的实验，应放到未来可执行环境阶段。

反事实变体目前只支持 T0 单阶段，用来检验一个决策轴改变时理由是否相应调整。它们不是完整分支剧情；不可对变体强行导出 T1。

## 4. 作者区与参评区

本仓库是作者/操作员区，包含 oracle、rubric 和示例答案。不能在这里启动参评 Agent，再用提示词要求它“不要偷看”。

`export` 强制把 participant packet 导出到仓库以外，仅放当前题面、已披露事实、实际历史和记录元数据。它会拒绝覆盖已有目录，并记录输入与源案例 SHA-256。

**这不是安全沙箱。**脚本不会阻止同机 Agent 越界读文件、读全局记忆、联网搜公开题库或发现兄弟目录。最初可用手工文本会话；若给参评 Agent 文件工具，必须由实际运行环境只挂载该 packet，并隔离题库、兄弟试验和全局 Skill/记忆。未验证隔离的运行，只能标注为非严格探索实验。

哈希用于版本定位和发现意外改动，不提供防恶意篡改的签名或远程证明。

## 5. 每次运行应记录

case_id、阶段、变体、案例摘要哈希、指令包内容与哈希、模型实际标识、客户端/版本、推理/温度等设置（不可取得则写 unknown）、工具和联网权限、记忆/全局指令状态、输入、问答、原始输出、执行时间和成本（可取得时）、异常/重试原因、评审人和结果。

`run_meta.json` 只自动填本地可知部分，不替操作者猜设置或用量。实际模型身份无法由这个脚本认证。运行失败、拒绝、超时和无效输出也要保存，不能只留下成功回答。

重试只能按预先写好的规则处理。不得给不满意答案额外澄清和重跑机会，然后与其他组的一次作答比较。

## 6. 最小试验规模

先用 `001-reporting/T0` 跑三组，每组一次，共三份回答，只用于检查流程是否通顺。

三个案例经人复核后，可运行：

```text
3 案例 × 3 阶段 × 3 组别 × 2 次独立重复 = 54 个阶段回答
3 案例 × 3 组别 × 2 次独立重复 = 18 条完整轨迹
```

先固定一个模型，不要同时研究模型差异。重复用于观察不稳定性，不会创造更多独立案例。**这仍只有三个案例家族，不是 54 个独立任务样本。**三个变体另算，也不能伪称全新独立案例。

样本极小时报告逐案例结果、错误类型、人工意见和成本，不宣称统计显著，不发布总体排行榜。未来估计不确定性时以案例家族为聚类单位，不把同一剧情的各阶段当独立样本。

## 7. 评审

参考 `RUBRIC.md`。先检查关键约束，确认违反时不能用其他分数补偿。再看六个维度，按回答中的证据评分，而非按作者喜欢的技术。

至少在校准阶段由两位有相关经验的人独立看同一部分材料；James 可以是其中之一。若暂时只有一个人，明确标为单人探索，不伪称经过独立专家共识。

隐藏模型名、arm 名称和执行顺序；随机交错回答顺序，保留映射表但不提供给评审者。不同输出格式可能使评审者猜到组别，因此只能声称隐藏元数据，不能声称完全双盲。

评审包包含该次**实际可见**的上下文和问答。评分笔记提供允许的解空间和不变量，但不能要求猜中未公开事实。LLM 可辅助整理证据和发现遗漏，不得担任未经人工校准的唯一裁判。[S6]

## 8. 不设置一个“架构 IQ”总分

初始报告保留三部分：关键约束结果、六维画像、人工理由与成本。时间、输出长度、澄清数量属于成本和行为指标，不自动代表质量。

候选指标定义：

- 关键约束失败：评审确认、且参评者可依据已披露事实避免的违反；分母是有结论的评审输出，另列无法判断数。
- 决策可接受性：多种可辩护方案均可进入 acceptable；不要求匹配作者答案。
- 澄清有效性：问题是否可能改变选择、风险或验证计划；由案例和评审理由支持，不等于问题数。
- 演化适切性：继续、变更、暂缓均可能正确；观察理由是否响应新的决策敏感事实。
- 人工修正负担：操作者实际记录纠正什么、为何纠正与耗时；接受率不是质量的替代指标。

不报告未经实际记录的节省比例、准确率、ROI 或胜率。未来若使用加权总分，必须先公开权重与硬约束处理，并证明它不会隐藏致命错误。

## 9. 污染与保留集

包内三个案例都是 development。后续新增 holdout 时应按案例家族拆分，不能把同一业务的 T0 放训练、T1 放测试，或把同一题换名当新题。

用于调 Skill 的案例不可继续称为独立 holdout。真实项目案例需要授权、匿名化、来源与时间记录；不得为了显得真实而拼凑客户信息。

公开教材与可信评测集要分开。发布后案例可能进入模型训练或被工具检索；未来公开分数应披露污染风险，不把“文件放 private”当作绝对无污染保证。

## 10. 当前已自动化与人工职责

脚本自动做结构检查、阶段顺序、有限版本一致性、题面白名单导出、问答计数和原始历史拼接。

人负责案例语义、问题映射、组间实验公平、运行环境隔离、模型执行、原始输出保存、盲评和质量判断。Schema 通过、脚本测试通过，都不等于架构建议正确或 Skill 有效。
