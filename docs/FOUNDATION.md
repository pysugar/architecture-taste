# 初始化基座：从架构知识到架构判断

## 1. 项目定位

**Architecture Taste 是一套帮助人和 Agent 在具体上下文中做架构决定、记录代价，并在事实改变后重新判断的方法与实验场。**

“品味”不是作者的技术偏好，也不是不可解释的审美权威。可操作的定义是：在当前信息与资源下，识别不可妥协的性质，比较有意义的选项，做出可以负责的决定，并知道什么事实会推翻它。

对外描述不宜写“全球首个”“填补空白”或“让 AI 获得资深架构师能力”。现有 ADR、ATAM、QAW、演化式架构和 Architectural Katas 已分别提供决策记录、质量场景、权衡和练习机制；Anthropic 的工程资料也明确谈到过度工程评测。这里的工作是把**上下文获取、阶段决策和反事实变化**组织成可回放协议，而不是重新发明整套软件架构学。[S1–S6]

最初的使用者是 James 自己，以及使用 Codex/Claude 等工具完成真实项目的人。先验证自用价值，再决定是否变成开源 Skill、训练案例集、顾问工作流或商业产品。

## 2. 四个需要验证的假设

H1：在相同模型、相同事实、相同工具与预算下，这套方法比简版 ADR 更少漏掉关键约束，更清楚地描述取舍。

H2：在事实不完整时，它提出的问题更可能改变决策；不是单纯问题更多、对话更长。

H3：新事实出现时，它能适当保持、延伸、替换或退役旧方案，且不因坚持历史立场或追求新颖而偏离约束。

H4：这些改善能在未参与提示调优的真实工程决策中带来实际收益，例如减少关键遗漏、降低人工修正负担、留下可用复核依据。

四项都是待验证假设。三份漂亮的回答不能证明 H4；充分上下文带来的收益也不能自动证明 H1。

## 3. 三条概念边界

### 不是“上下文齐全以后一定有最优答案”

有些信息取得成本太高，有些需求本来就冲突，还有些未来变化不可预测。目标不是穷尽事实，而是找到**足以改变当前决定的信息**，并管理剩余不确定性。

先问：这个未知会改变选项、风险或验证计划吗？如果不会，可以暂不调查。如果会，再比较询问、测量、试验的成本与潜在错误损失。这里采用信息价值的工作直觉，不声称已经有可计算且被验证的收益模型。

### 不是“永远选择最简单”

简单必须按业务不变量和团队拥有能力衡量。一个现成、被团队维护的平台，对应用团队的边际复杂度可能低于自建“小而美”运行环境。反之，没有运维归属的平台，再流行也不能当作低成本。

遵循的约束是：**满足当前必要性质，并避免无必要地关闭未来选择**。不是组件最少，也不是现在最便宜。预算、风险和需求冲突时，Agent 应明确暴露冲突，而不是擅自牺牲其中一项。

### 不是“代码真的等同于编译器 IR”

把源码看作可能下移的人机交互层，是有用的工作比喻；但 Agent 并非语义保持的编译器。自然语言要求不完备，生成过程也不能提供编译器式正确性保证。因此，本项目强调验证与责任，不以“不看代码”为目标。

## 4. 基本工作流

```text
需求 / 变更 / 异常
        ↓
最小上下文：事实、观察、假设、未知、偏好、硬约束
        ↓
找出决策敏感信息 → 询问 / 测量 / 小试验
        ↓
不可妥协的性质与失败语义
        ↓
两个或三个真实候选，包括适当的 keep / defer
        ↓
当前决定 + 为什么现在 + 接受的代价
        ↓
可验证承诺 + 复核触发器 + 责任人
        ↓
真实反馈 → 新决定，保留旧决定当时的依据
```

最小持久单元沿用 ADR，不再创造一个内容高度重复的新缩写。Nygard 的结构已经包括情境、决定、状态与后果；这里按需要补充未知、验证和复核条件。[S1]

## 5. 三份最小记录

**上下文卡**：本次业务结果、现状、硬约束、偏好、未知和证据时效。不是包含所有组织资料的大型上下文仓库。

**决定卡**：现在做什么、为什么、其他选择为何暂不采用、接受什么债务、谁确认。使用少量段落即可。

**验证与复核卡**：哪些性质必须验证、怎样验证、什么信号出现时重新打开此决定。触发器必须是“重新评估”而不是“自动上 Kafka”。

优先使用 `templates/context.md` 与 `templates/decision.md`；JSON Schema 用于后置规范化和机器检查，不强迫人把一次小决策写成表单工程。

## 6. 质量属性必须落到场景

“高可用”“高性能”“强一致”不是足够明确的验收条件。QAW 从业务目标识别关键质量属性；ATAM 用场景分析方案的风险、敏感点和取舍。[S2–S3]

本项目采用一个简化工作格式：在什么条件下，谁对哪个边界施加什么变化，系统应该如何响应，以及用什么证据判断。例：worker 在发布结果前后崩溃，恢复后受理任务仍可追踪，同一 job_id 对用户只出现一个有效结果。

这不是宣称“恰好一次执行”；它把执行重试和业务结果语义分开。验证可以是故障注入、状态检查、人工演练或受控压测；不能全部降格为静态格式检查。

## 7. 演化不是复杂度单调上升

演化至少有六类事件：工作负载变化、业务规则变化、失败代价变化、团队能力变化、外部依赖变化、产品退出。规模不变而值守团队撤销，可能足以改变部署决定；流量下降也不意味着可以放弃额度不超支的约束。

输出动作允许 `keep / extend / replace / retire / defer / investigate`。评价的不是改得多还是改得少，而是**在当前可见信息下，改变是否有理由，代价是否可接受**。

“为未来留空间”也需要成本界限。模块边界、稳定标识和可导出数据，可以在具体需求下值得保留；没有清晰收益的插件系统、通用事件总线、全球多活预留，不因未来可能有用就获得正当性。YAGNI 的讨论支持区分未证实未来需求与保持可修改性的工程实践。[S7]

## 8. Skill 和 Lab 是两个面，不是两个平台

**实践面**：把实验性 Skill 用于某个真实、有限的决定，记录你保留、修改和否决了什么。

**实验面**：使用合成案例做可控对照，避免只挑选看起来成功的示例。

两者初期都只使用 Git、Markdown/JSON 与一个本地脚本。不要先建向量库、图数据库、知识图谱、模型路由器、多 Agent 编排器、Dashboard 或复杂评分服务。

不做这些不是价值判断，而是当前没有证据表明它们是瓶颈。项目应当用自己的决策协议证明何时需要增加它们。

## 9. 实践落地的输出边界

日常决策默认只输出七项：决定、依据、取舍、暂不做、验证、复核、待人确认。可以短至一页，不必总画架构图。

适合第一次使用的题目是“某个后台任务需不需要引入持久队列”，而不是“重构全部研发平台”。先挑低后果、可回退、能取得事实的任务；涉及真实生产权限、数据删除或外部承诺的执行不在本基座授权内。

项目真正可能积累的资产，是**当时的信息、决定、代价、后来发生的变化与纠偏**。失败案例和“不需要改变”的案例，与成功迁移一样重要。

## 10. 价值验证与退出条件

如果普通 ADR 已经得到同样质量，本项目应缩短 Skill，而不是为了维持项目规模继续堆内容。

如果评分者主要争论个人风格，先修案例事实和评分边界。如果合成测试变好、真实任务没改善，说明迁移价值未得到证明。如果准确率略升但交互和阅读负担明显增加，要考虑只在高影响决策触发。

最早的成功，不是“收录 1000 个架构模式”，而是能准确回答：**哪类决定会被这套方法改善，改善从哪里来，它什么时候不值得启动。**
